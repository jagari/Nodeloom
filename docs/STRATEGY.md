# 제품 전략

이 문서는 "누구를 위해, 무엇을, 왜 우리가" 만드는지를 정한다. 기능 아이디어가 이 문서와 맞지 않으면 만들지 않거나, 먼저 이 문서를 PR로 고친다.
결정의 이력은 `docs/DECISIONS.md`(D11, D12)에 있고, 근거 조사는 `docs/research/pivot-options.md`에 있다.

마지막 갱신: 2026-10-13 (v2)

## 한 줄 정의

**학생·소규모 팀이 가진 맥·윈도우·리눅스·라즈베리파이·Jetson을 설치만 하면 자동으로 묶어, 한 화면에서 보고, 파일 묶음 작업을 기기들에 나눠 처리하는 도구.**

예: 팀원 노트북 3대와 동아리방 데스크톱 1대에 설치하고, 강의 녹음 40개를 끌어다 놓으면 네 기기가 나눠서 받아쓰기(전사)를 한다.

## 목표

1. **실사용자**: 팀 밖의 사람이 실제로 설치해서 쓴다.
2. **포트폴리오**: 팀원 각자가 맡은 부분을 설명하고 측정치로 보여줄 수 있다.

수익화는 지금 목표가 아니다(D11에서 보류).

## 사용자

| 순위 | 사용자 | 상황 | 줄이려는 고통 (가설) |
|---|---|---|---|
| P0 | **우리 팀** | 팀원 5명의 맥·윈도우 노트북, 데스크톱, 라즈베리파이 | 첫 사용자이자 첫 시험대(dogfooding) |
| P1 | **학생 팀** | 과제·프로젝트·동아리에서 기기가 제각각 | 오래 걸리는 작업을 한 대에서만 돌리고 나머지 기기는 논다. 여러 기기를 묶는 기존 도구는 설치·운영이 어렵다 |
| P2 | **홈랩 개인** | 집에 맥, PC, 라즈베리파이 등이 여러 대 | 기기 상태를 한곳에서 보고 남는 자원을 쓰고 싶다 |

**아직 확인하지 못한 것**: 학생 팀이 "여러 기기로 나눠 돌릴 작업"을 실제로 자주 갖고 있는지는 근거가 없다. 첫 검증 과제다.

## 강점 1: 플러그 앤 플레이

"쉽다"는 측정할 수 있어야 강점이 된다. 아래 숫자는 근거 있는 기준이 아니라 **팀이 확정할 제안값**이다.

| 항목 | 목표 |
|---|---|
| 설치 | 기기마다 설치 파일 1개 또는 명령 1줄. 설정 파일 0개 |
| 실행 | 재부팅 후 자동 실행(서비스 등록) |
| 발견 | 같은 네트워크의 허브를 자동으로 찾음(mDNS) |
| 연결 | 처음 한 번 대시보드에서 확인 코드를 보고 승인. 이후 자동 재연결 |
| 시간 | 설치를 시작해 대시보드에 기기가 뜰 때까지 2분 이내 |

**보안과의 균형**: "누구나 자동으로 붙는다"는 플러그 앤 플레이가 아니라 보안 사고다. 블루투스처럼 **처음 한 번만 사람이 승인**하고, 승인된 기기는 기기별 자격 증명으로 붙는다. 지금의 공유 토큰 방식은 이 흐름으로 바꾼다(P0).

## 강점 2: 이기종 지원

| 등급 | 플랫폼 | 대표 기기 | 비고 |
|---|---|---|---|
| 1등급 | macOS arm64 | 애플 실리콘 맥 | GPU 지표는 권한 문제 조사 중(#17) |
| 1등급 | Windows x64 | 게이밍 PC, 노트북 | NVIDIA 지표(#16) |
| 1등급 | Windows arm64 | 윈도우 ARM 노트북 | 빌드·검증 필요 |
| 1등급 | Linux x64 | 서버, 데스크톱 | |
| 1등급 | Linux arm64 | 라즈베리파이 4·5, NVIDIA Jetson | Jetson GPU 지표 방식은 조사 필요 |

**라즈베리파이의 역할**: 외장 GPU가 없으면 무거운 계산 노드로는 약하다. 대신 전기를 적게 쓰고 24시간 켜 둘 수 있어서 **항상 켜 두는 허브(마스터)** 로 권장한다. 그러면 노트북을 닫아도 대시보드와 작업 큐가 살아 있다.

## 경쟁 지형

확인일은 2026-10-12~13이다. 표시 기준은 **원문**(페이지를 직접 읽음)과 **요약**(검색 결과 요약만 확인함)이다.

| 도구 | 하는 일 | 우리와 겹치는 점 | 우리와 다른 점 |
|---|---|---|---|
| **Beszel** | 경량 허브·에이전트 서버 모니터링. 에이전트 RAM 약 10~15MB, 라즈베리파이 적합, NVIDIA·AMD·Intel GPU 지표. 웹에서 기기 추가 후 키 전달 — 요약 ([블로그](https://akashrajpurohit.com/blog/beszel-selfhosted-server-monitoring-solution/)) | 이기종 관측, 쉬운 설치 | 작업을 나눠 처리하지 않는다 |
| **Netdata** | 무료 오픈소스 모니터링. 리눅스·macOS·FreeBSD·윈도우 설치 안내, 설정 없이 초 단위 지표 — 요약 ([문서](https://learn.netdata.cloud/docs/get-started)) | 이기종 관측 | 작업을 나눠 처리하지 않는다 |
| **Slurm** | 클러스터 작업 스케줄러. 무료지만 설치·운영이 무겁다 — 요약 (`docs/research/pivot-options.md`) | 작업 분산 | 비전문가 학생 팀이 쓰기 어렵다(가설) |
| **dstack, SkyPilot** | GPU 서버·클라우드 작업 실행 — 요약 (`docs/research/pivot-options.md`) | 작업 분산 | 서버·클라우드 중심이다. 섞인 개인 기기는 주 대상이 아니다(가설) |
| **exo** | 여러 기기로 LLM 분할 추론, 자동 발견, 내장 대시보드. 맥 중심, 리눅스는 CPU만 — 원문 ([GitHub](https://github.com/exo-explore/exo)) | 자동 발견, 이기종 | AI 추론 전용이다 |
| **CrowdRender, Flamenco** | 여러 기기로 Blender 렌더 — 요약 (D10) | 작업 분산 | Blender 전용이다 |

**차별점 가설**: 관측 도구(Beszel·Netdata)는 **보기만** 하고, 분산 도구(Slurm 등)는 **전문가용**이며, 나머지는 **특정 작업 전용**이다. 우리는 "비전문가가 설치만 하면 섞인 기기들이 묶이고, 검증된 작업을 나눠 처리하는" 자리를 노린다. 이 자리에 실제 수요가 있는지는 아직 검증하지 않았다.

## 작업 모델과 보안

에이전트는 **네트워크로 받은 명령 문자열을 실행하지 않는다**(절대 규칙 1번). 작업은 두 가지로만 표현한다.

1. **내장 플러그인**: 우리가 만들고 테스트한 작업 종류다. 닫힌 enum이며, 각 플러그인은 고정된 프로그램과 검증된 인자만 쓴다.
   - 첫 번째: **Whisper 배치 전사**(P1)
   - 후보: AI 엔진·모델 감지(관측형), 영상 변환
   - 기존 Blender 렌더(보류 상태로 유지)
2. **기기 주인 템플릿**(P2, 구현 전 설계·보안 검토):
   - 각 기기 주인이 **자기 기기의 로컬 설정 파일**에 "프로그램 + 허용하는 인자 형식"을 등록한다.
   - 마스터는 템플릿 **이름과 검증된 값**만 보낼 수 있다.
   - 네트워크로 템플릿을 추가하거나 바꿀 수 없다.

**왜 Whisper가 첫 플러그인인가(추론, 실측 필요)**: 입력인 음성 파일은 작고 계산량은 크다. 그래서 와이파이처럼 느린 링크에서도 전송 시간보다 계산 이득이 커지기 쉽다. 파일 단위로 나누면 되므로 분할도 단순하고, 강의 녹음처럼 학생에게 쓸모가 분명하다.

## 하지 않을 것

- 네트워크로 받은 명령 문자열 실행. 기기 주인 템플릿도 P2 결정 전에는 만들지 않는다.
- "모든 작업이 빨라진다"는 주장. 독립 단위로 나눌 수 있는 작업만 빨라진다.
- 실시간 뷰포트·게임 fps 가속. 기기 간 연결(Thunderbolt 약 5GB/s)이 GPU 메모리 대역폭(수십~수백 GB/s)보다 훨씬 느리다.
- 추론 엔진이나 렌더러 자체 개발. 기존 프로그램을 감싸서 쓴다.

## 로드맵

각 단계는 "끝났다"의 기준을 만족해야 다음 단계로 간다.

### P0. 꽂으면 묶인다

- **페어링 승인**: 대기 기기 목록, 확인 코드, 기기별 자격 증명
- **지원 기기 빌드와 CI**: linux-arm64, windows-arm64
- **설치와 자동 실행**: 설치 파일, 서비스 등록(#9)
- **GPU 지표**: NVIDIA(#16), Apple(#17), Jetson(조사)
- **실기기 검증**: 맥(#1), 윈도우(#4), 라즈베리파이·Jetson, mDNS(#2), 앱 창 연결(#3)
- **화면**: 기기별 GPU 카드(#19)
- **끝났다의 기준**: 팀 기기 4대 이상(OS 3종 이상)을 각각 2분 안에 설치·승인하고, 일주일 동안 대시보드에 안정적으로 보인다.

### P1. 나눠서 처리한다

- **파일 묶음 작업 모델**: 입력 파일 배포, 결과 수집(#5), 실패 시 재시도
- **성능 차이를 반영한 분배**(#14): 작업을 잘게 나눠 먼저 끝난 기기가 다음 조각을 가져가는 방식(작업 훔치기)
- **Whisper 배치 전사 플러그인**
- **기기 간 링크 측정**(#20): 파일 전송 계획에 쓴다
- **끝났다의 기준**: 실제 강의 녹음 묶음을 전사하고, 1대와 N대의 소요 시간을 같은 조건에서 실측해 기록한다.

### P2. 내 작업도 넣는다

- 기기 주인 템플릿. 설계와 위협 모델(누가 무엇을 할 수 있나)을 먼저 문서로 쓰고, 팀이 결정한 뒤 구현한다.

### P3. 플러그인 확장

- AI 엔진·모델 감지(#18), 영상 변환, Blender 정리
- 원격 접근이 필요해지면 그 전에 TLS를 적용한다(#6).

## 성공 지표

아래 숫자는 **팀이 확정할 제안값**이다.

| 지표 | 제안 목표 |
|---|---|
| 설치부터 대시보드 표시까지 | 기기당 2분 이내 (OS별 실측) |
| 팀 dogfooding | 기기 4대 이상, OS 3종 이상, 2주 연속 운영 |
| 실제 작업 | 강의 녹음 등 실제 파일 묶음을 이 도구로 처리, 1대 대비 소요 시간 실측 |
| 팀 밖 사용 | 다른 학생 팀 1곳 이상 |
| 대화한 사용자 | 5명 이상 |

## 기술 위험 (먼저 확인할 것)

| 위험 | 확인 방법 |
|---|---|
| Whisper 구현 선택. whisper.cpp 같은 명령행 프로그램을 셸 없이 인자 목록으로 실행하는 방식이 유력하나 미검증 | Whisper 플러그인 이슈에서 스파이크 |
| 기기별 가속 차이(Metal·CUDA·CPU)로 속도가 크게 달라짐 | 성능 반영 분배(#14)로 흡수. 기기별 실측 |
| 모델 파일 크기와 기기별 배포 | 파일 묶음 작업 모델에서 설계 |
| 윈도우 ARM·Jetson 빌드와 GPU 지표 | 빌드·CI 이슈, 실기기 검증 이슈 |
| mDNS가 다른 서브넷·VPN을 넘지 못함 | 수동 주소 입력을 대안으로 유지. 실네트워크 검증(#2) |
| 맥 GPU 지표의 관리자 권한 필요 여부 | #17 |

## 기존 코드에서 쓰는 것

- **그대로 재사용**:
  - 에이전트·마스터 연결, mDNS 자동 발견
  - 작업 분배와 기기 이탈 시 재배정(`nodeloom-master/src/state.rs`)
  - `Runner` 구조(플러그인의 바탕)
  - 셸 없이 인자 목록으로 실행하는 방식(Blender 러너)
  - 작업 검증, 대시보드 컴포넌트
- **바꿈**: 공유 토큰 → 페어링 승인. 프레임 범위 분할 → 파일 묶음 분할(프레임 분할은 Blender 플러그인에 남김).
- **새로 만듦**: GPU 지표, 파일 전송, Whisper 플러그인, 설치·서비스 등록, arm64 빌드.
