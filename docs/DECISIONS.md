# 결정 기록

중요한 결정은 여기에 한 항목씩 추가한다. 이미 내린 결정을 뒤집을 때도 지우지 말고 새 항목을 추가해 이유를 남긴다.
형식: 날짜 · 결정 · 이유 · 영향.

## D1. 작업 분산만 하고 실시간 가속은 하지 않는다 (2026-10-12)

- **결정**: 렌더링·빌드처럼 독립 단위로 나눌 수 있는 작업만 분산한다. 뷰포트나 게임 실행 fps는 다루지 않는다.
- **이유**: 기기 간 연결(Thunderbolt 약 5GB/s)이 GPU 메모리 대역폭(수십~수백 GB/s)보다 훨씬 느리고, 프레임마다 왕복 지연이 생긴다.
- **영향**: 마케팅과 문서에서 "노트북이 빨라진다"는 식의 표현을 쓰지 않는다.

## D2. 제품 이름은 nodeloom (2026-10-12)

- **결정**: 처음 정한 `nodeweave` 대신 `nodeloom`을 쓴다.
- **이유**: npm에 같은 이름(`nodeweave`, 웹 시각화 라이브러리)이 이미 있었다. `nodeloom`은 crates.io·npm·PyPI 모두 비어 있었다.
- **영향**: 도메인과 상표(KIPRIS, USPTO 제9·42류)는 아직 확인하지 못했다. 유료 판매 전에 확인한다. 앱 식별자는 임시로 `io.github.jagari.nodeloom`이다.

## D3. 코어는 Rust, UI는 Tauri + Svelte (2026-10-12)

- **결정**: 에이전트·마스터는 Rust, 데스크톱 UI는 웹 기술(Svelte·TypeScript)을 Tauri로 감싼다. Flutter는 쓰지 않는다.
- **이유**: 코어가 Rust라 Tauri는 브리지 계층 없이 붙는다. 대시보드(차트·표)는 웹 생태계가 유리하다. 단일 실행 파일로 맥·윈도우·리눅스에 배포하기 쉽다.
- **영향**: 팀 대부분이 Rust 경험이 없어, Rust 영역은 담당 A의 리뷰를 필수로 한다.

## D4. UI와 코어는 로컬 API로 분리한다 (2026-10-12)

- **결정**: UI는 마스터의 HTTP/WebSocket API만 쓴다. Tauri 전용 명령(IPC)은 만들지 않는다.
- **이유**: 나중에 모바일 앱이나 웹 대시보드를 같은 API에 붙일 수 있고, UI 프레임워크 선택을 되돌릴 수 있게 된다.
- **영향**: 다른 출처의 UI가 API를 부르므로 마스터는 CORS를 허용한다(토큰 인증이라 안전).

## D5. 작업은 닫힌 enum이고 임의 명령은 실행하지 않는다 (2026-10-12)

- **결정**: 작업 종류는 `TaskPayload` enum으로 고정한다. 검증은 마스터와 에이전트 양쪽에서 하고, 외부 프로그램은 셸 없이 실행하며, Blender는 `--disable-autoexec`로 실행한다.
- **이유**: 에이전트는 네트워크로 받은 지시를 실행하는 프로그램이라, 범용 명령 실행을 허용하면 같은 네트워크의 누구나 원격 코드 실행을 할 수 있게 된다. `.blend` 파일은 내장 파이썬 스크립트를 담을 수 있다.
- **영향**: 새 작업 종류는 proto 변경과 검증 규칙 추가가 필요하다.

## D6. 수익 모델은 오픈코어 (2026-10-12)

- **결정**: 코어는 Apache-2.0 오픈소스로 공개한다. Pro 기능(기기 수 확장, 작업 우선순위, 이력·리포트, 알림, 추가 러너, 원격 접속)은 별도 비공개 저장소에 둔다. 결제는 판매대행(MoR) 서비스를 검토한다.
- **이유**: 무료 코어로 사용자를 모으고, 이미 공개한 코드의 라이선스를 바꿀 일이 생기지 않게 한다.
- **영향**: 외부 기여를 받으면 라이선스 변경이 어려워지므로, 받기 전에 CLA 또는 DCO를 정한다. 가격은 사용자 인터뷰 후에 정한다(가설: 월 $5~9 또는 평생 $49~79).

## D7. Tauri 셸은 Cargo 워크스페이스에서 뺀다 (2026-10-12)

- **결정**: `apps/desktop/src-tauri`는 별도 `Cargo.lock`과 빌드 폴더를 쓴다.
- **이유**: 리눅스에서 Tauri를 빌드하려면 WebKitGTK 등 GUI 라이브러리가 필요하다. 코어 테스트(`cargo test --workspace`)가 그 라이브러리 없이 돌아야 한다.
- **영향**: CI에 데스크톱 셸 빌드를 별도 작업으로 둔다.

## D8. UI는 TypeScript 6에 고정 (2026-10-12)

- **결정**: `typescript`를 `~6`으로 고정한다.
- **이유**: svelte-check 4.7이 TypeScript 7 단독 설치를 지원하지 않는다.
- **영향**: svelte-check가 TypeScript 7을 지원하면 다시 검토한다.

## D9. 작업 관리는 GitHub Issues, 컨텍스트는 저장소에 (2026-10-12)

- **결정**: 할 일과 담당자는 GitHub Issues로 관리한다. 팀과 LLM이 공유할 규칙·배경은 저장소 파일(`AGENTS.md`, `docs/`)에 둔다.
- **이유**: 팀원 5명이 서로 다른 LLM 도구(Claude, ChatGPT, Codex, Gemini)를 쓴다. 채팅 기록은 공유되지 않으므로 저장소가 유일한 공통 기준이어야 한다.
- **영향**: 규칙 원본은 `AGENTS.md` 하나이고, `CLAUDE.md`와 `GEMINI.md`는 그것을 가져온다. 채팅형 도구에는 `scripts/llm-context.py` 출력을 붙여 넣는다.

## D10. 경쟁 조사 정정: 직접 경쟁 제품이 있다 (2026-10-12)

- **결정**: "개인이 가진 기기를 묶는 도구는 비어 있는 영역"이라는 이전 판단을 철회한다. 기능 개발보다 사용자 인터뷰(이슈 #11)를 먼저 해서 계속할지 방향을 바꿀지 정한다.
- **이유**: 처음 조사에서 다음 제품들을 놓쳤다.
  - **CrowdRender**: 사용자의 노트북·데스크톱을 묶어 렌더하는 Blender 애드온. 한 프레임 분할을 지원하고, 무료 오픈소스판과 유료판이 있다. 판매처마다 가격 표기가 다르다. ([Superhive](https://superhivemarket.com/products/distributed-rendering-addon), 2026-10-12 확인)
  - **SheepIt**: 무료 커뮤니티 렌더팜. ([gamedev.tv](https://gamedev.tv/articles/using-sheepit-render-farm), [Arch Wiki](https://wiki.archlinux.org/title/Sheepit), 2026-10-12 확인)
  - 클라우드 렌더팜도 판매자 계산으로 RTX 5090에서 4분 걸리는 프레임이 약 $0.21이다. 개인 규모 작업에서 "비용 절감"은 강한 이유가 되기 어렵다. ([Super Renders Farm](https://superrendersfarm.com/article/render-farm-cost-per-frame-breakdown-2026), 판매자 자료)
- **영향**:
  - D-Lab 수행계획서의 국내외 현황·차별성을 고쳤다. 차별성은 이미 가진 장점이 아니라 "검증할 가설"로 표현한다.
  - CrowdRender 대비 부족한 점을 이슈로 남겼다: 한 프레임 분할, 기기 성능 가중치 분할.
  - D6(오픈코어 수익 모델)과 가격 가설은 인터뷰 결과가 나올 때까지 보류한다.
  - 방향 전환 후보 조사는 `docs/research/`에 정리한다.

## D11. 1차 타겟을 로컬 AI 클러스터의 관측·진단으로 바꾼다 (2026-10-12)

- **결정**:
  - 1차 타겟을 "여러 기기로 로컬 LLM을 돌리는 개인과 소규모 팀"으로 바꾼다.
  - 제품은 엔진(Ollama, llama.cpp, exo)에 상관없이 맥·윈도우·리눅스 노드를 관측하고 진단하는 도구로 정의한다(`docs/STRATEGY.md`).
  - 목표는 실사용자와 포트폴리오다. D6(오픈코어 수익화)는 보류한다.
- **이유**:
  - Blender 분산 렌더는 무료 Flamenco와 유료 CrowdRender 사이에서 "기능이 더 적은 대안"이다(D10, `docs/research/pivot-options.md`).
  - 연구실 GPU 공유는 학교 안 접근 경로가 없어 검증이 어렵다.
  - 로컬 AI는 관심이 크고(exo ★47.8k, LocalAI ★49.5k), llama.cpp RPC처럼 발견·UI·모니터링이 없는 엔진이 있다. 무엇보다 **팀원 기기로 직접 써 보며 검증할 수 있다.**
- **버린 대안**: (a) Blender 분산 렌더 고도화, (b) 연구실·동아리 GPU 공유. 코드와 이슈는 지우지 않고 보류한다.
- **실행 정책**:
  - 에이전트는 관측 중심이다. 절대 규칙 1번(임의 명령 금지)은 그대로 둔다.
  - 엔진을 고정 설정으로 실행하는 기능(로드맵 P2)은 규칙 1번 안에서 가능하지만, 시작 전에 이슈 합의와 A 승인을 거쳐 새 결정으로 기록한다.
- **위험과 재검토 조건**:
  - "모니터링이 없어서 힘들다"는 불만은 조사에서 직접 확인되지 않았다.
  - 엔진들이 대시보드를 내장하는 추세다(exo, LocalAI 4.10, GPUStack).
  - dogfooding 기록과 인터뷰에서 관측·진단이 상위 고통으로 나오지 않으면 방향을 다시 검토한다.

## D12. 이기종 기기 플러그 앤 플레이 풀 + 작업 분산으로 조정 (2026-10-13)

- **결정** (팀장 결정, `docs/STRATEGY.md` v2):
  - **핵심**: 범용 기기 통합. macOS, Windows(x64·ARM), Linux(x64·arm64, 라즈베리파이, Jetson).
  - **강점**: 플러그 앤 플레이(설치 1번, 설정 0개, 화면 승인 1회, 2분 이내 표시 — 제안값).
  - **목적**: 자원을 묶어 파일 묶음 작업을 나눠 처리한다. 첫 플러그인은 Whisper 배치 전사다.
  - **1차 사용자**: 학생·소규모 팀. 우리 팀이 첫 사용자다.
  - **AI**: AI 엔진·모델 감지는 플러그인 중 하나다.
  - **페어링**: 공유 토큰을 "처음 한 번 화면에서 승인 → 기기별 자격 증명"으로 바꾼다.
  - **실행 범위**: 내장 플러그인 + 기기 주인이 자기 기기 로컬 설정에 등록한 템플릿. 템플릿은 P2에서 설계·보안 검토 후 구현한다.
- **D11에서 바뀐 점**:
  - "관측 중심" → "관측 + 작업 분산"
  - "로컬 AI 클러스터가 1차 타겟" → "AI는 플러그인"
  - 수익화 보류와 "실사용자 + 포트폴리오" 목표는 그대로다.
- **절대 규칙 1번 변경**: "닫힌 enum만"에서 "네트워크로 받은 명령 문자열은 실행하지 않음. 내장 플러그인과 기기 로컬 템플릿만"으로 바꿨다. 명령 문자열이 네트워크로 오가지 않으므로 원래 취지(같은 네트워크의 누구도 팀원 기기를 조종할 수 없음)는 유지된다.
- **이유**:
  - 팀장이 이기종 통합과 플러그 앤 플레이를 핵심 가치로 판단했다.
  - 학생 팀은 기기가 제각각이라 이기종 지원이 곧 사용 조건이 된다.
  - Whisper 배치는 입력이 작고 계산이 커서, 느린 네트워크에서도 분산 이득이 남기 쉽다(추론, 실측 필요).
- **위험**:
  - 관측만 보면 Beszel·Netdata가 이미 이기종과 쉬운 설치를 제공한다(검색 요약 기준). 그래서 우리 차별점은 작업 분산에 걸려 있다.
  - 작업 분산은 처음의 Blender 방향(D10)과 같은 계열이다. "학생 팀이 나눠 돌릴 작업을 실제로 갖고 있는가"는 아직 검증되지 않았다. dogfooding(#15)과 인터뷰(#11)로 먼저 확인한다.

## D13. 페어링: 기기별 서명 키, 화면 승인, 영구 제거 (2026-10-13, #22)

- **결정**:
  - **기기 신원**: 에이전트가 직접 만든 Ed25519 키다. 마스터의 nonce에 서명해 증명하고, 비밀키는 보내지 않는다. 마스터는 공개키만 저장한다(`devices.json`).
  - **확인 코드**: 공개키 SHA-256에서 뽑은 6자리. 기기 로그·`nodeloom-agent pairing-code`와 대시보드에 같은 숫자가 뜬다.
  - **승인 전 기기**: 대기 목록에만 있고 작업·클러스터 정보를 받지 못한다. 대기 중 보낸 메시지는 버린다.
  - **제거 = 영구 취소**: 제거한 키는 토큰을 내도, 재시작 후에도 거부한다. 다시 붙이려면 그 기기에서 `reset-identity`로 새 키를 만들고 새 코드로 승인한다.
  - **무시**: 마스터 재시작 전까지 그 키를 대기 목록에 다시 올리지 않는다(메모리만).
  - **UI 인증**: 관리 토큰을 유지한다. 마스터 데이터 폴더의 `admin-token`(0600)에 저장해 재시작해도 그대로 두고, 처음에만 출력한다. `--rotate-admin-token`으로 바꾼다. 루프백 예외는 두지 않는다. 나중에 Tauri 셸이 마스터를 직접 띄우면 이 파일을 읽어 자동 입력한다(D4의 "UI는 API 클라이언트일 뿐"에서 좁은 예외).
  - **에이전트 `--token`**: 선택 옵션으로 남긴다(팀장 결정). 맞는 관리 토큰을 내면 화면 승인 없이 자동 승인한다. 단 `--master`를 직접 지정했을 때만 쓸 수 있다. 탐색으로 찾은 마스터(가짜일 수 있음)에는 토큰을 보내지 않는다. `--master`가 `.local` 같은 이름이면 운영체제가 mDNS로 풀 수 있어 경고한다. 토큰을 둔 기기를 제거하면 관리 토큰도 바꿔야 한다(그 기기에 토큰이 남아 있다).
  - **빈 토큰 거부**: `NODELOOM_TOKEN=`처럼 빈 값은 마스터·에이전트 모두 시작을 거부하고, 빈 관리 토큰은 어떤 값과도 일치하지 않는다(구현 리뷰에서 찾은 결함).
  - `PROTOCOL_VERSION`을 2로 올렸다. v1 에이전트는 "protocol 1 is not supported"로 거부된다.
- **이유**:
  - 키를 그대로 보내는 방식(초안)은 mDNS에 먼저 답한 가짜 마스터가 키를 받아 진짜 마스터에 재사용할 수 있었다. 설계 검토(보안·동시성·UX 3관점, 28개 지적)에서 가장 큰 문제로 나와 서명 방식으로 바꿨다.
  - 제거한 기기가 같은 코드로 다시 대기 목록에 오르면, 키를 훔친 사람과 진짜 기기를 화면에서 구별할 수 없다. 그래서 제거를 영구 취소로 정했다.
  - 관리 토큰을 매번 새로 만들면 마스터를 재시작할 때마다 대시보드에 다시 입력해야 해서 플러그 앤 플레이에 어긋난다.
- **남은 위험**: 통신이 평문이라 엿볼 수 있는 공격자는 관리 토큰을 훔칠 수 있고, 가짜 마스터는 연결 하나를 중계할 수 있다. TLS(#6)에서 확인 코드에 인증서 지문을 섞어 막는다. 위협 모델 표는 `docs/ARCHITECTURE.md` "보안 모델".

## D14. ARM 빌드: 네이티브 ARM 러너에서 테스트, 리눅스 배포는 musl 정적 링크 (2026-10-19, #23)

- **결정**:
  - CI의 Rust 작업에 `ubuntu-24.04-arm`(라즈베리파이·Jetson 대표)과 `windows-11-arm`을 더해, x64와 똑같이 fmt·clippy·테스트를 **모든 PR과 `main`에서** 돌린다(팀장 결정).
  - 배포용 바이너리는 별도 `binaries` 워크플로가 `main`과 수동 실행 때 만든다. 리눅스는 `*-unknown-linux-musl` 정적 링크, 윈도우는 MSVC, 맥은 arm64.
- **이유**:
  - 교차 컴파일(`cross`, zig)은 빌드만 확인하고 테스트는 못 돌린다. GitHub ARM 러너는 2026년 1월부터 비공개 저장소에서도 쓸 수 있어([변경 기록](https://github.blog/changelog/2026-01-29-arm64-standard-runners-are-now-available-in-private-repositories/)) 실제 arm64에서 테스트까지 돌릴 수 있다.
  - 라즈베리파이 OS와 JetPack은 glibc가 빌드 러너보다 오래돼, glibc 링크 바이너리는 "GLIBC_2.39 not found"로 실행되지 않는다. 정적 링크면 배포판과 무관하게 실행된다. 의존성이 순수 Rust라 추가 도구 없이 빌드된다(로컬에서 x86_64 musl 빌드와 전체 테스트로 확인).
- **비용**: 비공개 저장소라 ARM 러너 시간은 계정의 무료 분량에서 빠진다(러너당 2 vCPU). PR마다 대략 10분이 더 든다. 맥 러너는 분 단위 비용이 커서 바이너리는 `main`과 수동 실행 때만 만든다.
- **남은 일**: 실기기 실행 확인은 #24. Tauri 데스크톱 셸의 ARM 빌드는 아직 없다.

## D15. 팀 내부 베타: 마스터가 대시보드를 직접 제공하고, 태그로 릴리즈한다 (2026-10-26, #30)

- **결정**:
  - **배포 대상**: 팀 내부 베타. 저장소는 비공개로 두고 GitHub Releases에 올린다(팀장 결정). 받으려면 저장소 접근 권한이 있어야 한다.
  - **대시보드 제공**: 릴리즈 빌드의 마스터가 웹 UI를 바이너리에 담아 직접 제공한다(`embed-ui`). 사용자는 브라우저만 있으면 된다. 첫 실행 링크에 토큰을 URL 조각으로 넣어, 토큰을 손으로 옮기지 않아도 된다.
  - **설치**: 플랫폼별 압축 파일에 `install.sh`/`install.ps1`을 넣는다. 사용자 폴더(`~/.local/bin`, `%LOCALAPPDATA%\Nodeloom\bin`)에 설치해 관리자 권한이 필요 없다. 압축 파일 없이도 `gh`로 최신 릴리즈를 받아 체크섬을 확인한다.
  - **릴리즈 절차**: `CHANGELOG.md`에 버전 절을 쓰고, `Cargo.toml` 버전과 같은 `v*` 태그를 붙인다. 워크플로가 패키지와 `SHA256SUMS`를 올린다. `-beta` 같은 접미사가 있으면 pre-release로 표시하고, 마지막에 그 릴리즈에서 다시 설치해 확인한다.
  - **태그를 푸시할 수 없을 때**: Actions → `binaries` → Run workflow에서 `main`을 고르고 "release"를 체크해 실행한다. 같은 릴리즈를 만들고, 릴리즈가 `v<Cargo.toml 버전>` 태그를 그 커밋에 직접 만든다. 이미 있는 태그는 옮기거나 다시 쓰지 않는다(그 버전이 이미 나갔다는 뜻이므로 버전부터 올린다).
- **이유**:
  - Tauri 앱 설치 파일(.dmg·.msi)은 서명과 OS별 패키징이 필요해 베타에 비해 무겁다. 마스터가 UI를 제공하면 기존 API를 그대로 쓰면서(D4) 설치할 것이 바이너리 두 개로 줄어든다.
  - D4의 "UI는 API 클라이언트일 뿐"은 유지된다. 마스터는 정적 파일만 내주고, 데이터는 여전히 토큰이 필요한 API로만 오간다.
- **남은 일**: 부팅 시 자동 실행과 OS별 설치 파일(#9), 코드 서명, 공개 배포 여부 결정.
