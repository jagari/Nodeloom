# 아키텍처

코드를 바꾸면서 이 문서와 다른 동작을 만들었다면 같은 PR에서 이 문서도 고친다.

## 구성 요소

```
 ┌──────────────┐  HTTP / WebSocket (/api, /ws/ui)  ┌──────────────────┐
 │ 데스크톱 UI    │ ────────────────────────────────▶ │ nodeloom-master  │
 │ (Tauri+Svelte)│ ◀──── 클러스터 스냅샷(JSON) ───── │ 상태·스케줄링·API │
 └──────────────┘                                   └────────▲─────────┘
                                                             │ WebSocket (/ws/agent)
                                      ┌──────────────────────┼──────────────────────┐
                                      │                      │                      │
                               ┌──────┴──────┐        ┌──────┴──────┐        ┌──────┴──────┐
                               │ agent (맥)   │        │ agent (맥)   │        │ agent (PC)  │
                               │ Runner들     │        │ Runner들     │        │ Runner들     │
                               └─────────────┘        └─────────────┘        └─────────────┘
```

- **master** (`crates/nodeloom-master`): 한 대에서 실행한다. 에이전트 연결을 받고, 작업을 나누어 보내고, UI에 상태를 제공한다. 기본 포트는 `7878`이다.
- **agent** (`crates/nodeloom-agent`): 작업할 모든 기기에서 실행한다. 자원 사용량을 보고하고 배정받은 작업을 `Runner`로 실행한다.
- **UI** (`apps/desktop`): 마스터 API의 클라이언트일 뿐이다. 같은 API를 쓰는 다른 클라이언트(웹, 모바일)를 나중에 붙일 수 있다.
- **proto** (`crates/nodeloom-proto`): 위 셋이 주고받는 모든 메시지 타입. UI 쪽 사본은 `apps/desktop/src/lib/types.ts`(손으로 맞춤).

## 연결과 탐색

- 마스터는 mDNS로 `_nodeloom._tcp.local.`을 알린다(`--no-mdns`로 끔).
- 에이전트는 `--master host:port`가 없으면 mDNS로 마스터를 찾는다(최대 30초).
- Thunderbolt Bridge도 운영체제가 IP 네트워크로 잡으므로 LAN과 같은 경로를 쓴다.
- 연결이 끊기면 에이전트는 1초부터 최대 30초까지 간격을 늘리며 다시 접속한다. 승인까지 마친 연결이 끊긴 뒤에는 1초부터 다시 센다(마스터 재시작 직후 빨리 붙도록).

## 페어링 (처음 한 번 화면에서 승인, `docs/DECISIONS.md` D13)

### 기기 신원

- 에이전트는 처음 실행할 때 **기기 ID(UUID)와 Ed25519 키**를 만들어 `identity` 파일 하나에 저장한다.
  - 위치: `--state-dir`(env `NODELOOM_STATE_DIR`), 기본은 사용자 로컬 데이터 폴더의 `nodeloom/`(리눅스 `~/.local/share/nodeloom`, 맥 `~/Library/Application Support/nodeloom`, 윈도우 `%LOCALAPPDATA%\nodeloom`). 윈도우의 로밍 설정 폴더는 다른 PC로 복사될 수 있어 쓰지 않는다.
  - 유닉스에서 폴더 0700, 파일 0600으로 처음부터 만든다(`nodeloom_core::private_file`). 파일이 깨졌으면 새로 만들지 않고 오류를 낸다(조용히 새 기기가 되는 것을 막는다).
- 비밀키는 기기 밖으로 나가지 않는다. 연결할 때마다 마스터의 무작위 값(nonce)에 서명해 증명한다.

### 핸드셰이크

```
agent  → master  Hello { protocol, public_key, info, token? }   10초 안에 Proof까지 끝내야 함
master → agent   Challenge { nonce }                            32바이트 무작위 hex
agent  → master  Proof { signature }                            "nodeloom-hello-v2\n<nonce>\n<node_id>"에 서명
master → agent   Welcome | Pending | Rejected { reason }
                 Pending이면 연결을 유지하고, 결정되면 Welcome 또는 Rejected
```

마스터는 Hello를 받으면 다음 순서로 확인한다(`server.rs` `handshake`, `state.rs` `classify`).
1. 8KiB를 넘는 Hello는 거부한다. `type`과 `protocol`만 먼저 읽어, 버전이 다르면 읽을 수 있는 이유와 함께 거부한다.
2. `validate_node_info`: 기기 ID는 `[A-Za-z0-9_-]` 1~64자, 호스트명·OS·아키텍처는 64자 이하이고 제어 문자와 유니코드 기본 무시 문자(양방향 제어, 폭 0 문자, 변형 선택자, 태그 문자 등)가 없어야 한다. 에이전트는 보내기 전에 자기 정보를 이 규칙에 맞춘다(`fit_node_info`: 숨은 문자 제거, 긴 호스트명은 첫 레이블만, 64자로 자름).
3. 서명 검증(`verify_strict`). 실패하면 거부한다.
4. 판정:

| 상황 | 결과 |
|---|---|
| 제거(취소)된 키 | 거부. 토큰이 있어도, 재시작 후에도 |
| 같은 ID + 같은 키로 승인됨 | Welcome |
| 같은 ID가 다른 키로 승인됨 | 거부("대시보드에서 먼저 제거") |
| 키가 다른 ID로 승인됨 | 거부 |
| 관리 토큰을 냄 | 맞으면 자동 승인 후 Welcome, 틀리면 거부(대기로 넘기지 않음) |
| 이번 실행에서 "무시"한 키 | 거부 |
| 그 외 | 대기 목록에 넣고 Pending |

- 승인 확인과 노드 등록은 같은 락 안에서 한다(`Cluster::admit`). 제거 직후의 연결이 끼어들 수 없다. `Welcome`은 등록 직후, 대기 중인 작업 배정 메시지보다 먼저 보낸다.
- 대기 중인 연결에서 온 메시지는 읽고 버린다. 대기 기기는 `nodes`에 없으므로 작업 배정 대상이 아니고 스냅샷도 받지 않는다.
- 마스터는 대기 연결에 15초마다 Ping을 보내고 45초 동안 아무것도 오지 않으면 끊는다. 에이전트는 대기 중 60초 동안 아무 프레임도 없으면 다시 접속한다.

### 확인 코드

- 공개키의 SHA-256 앞 4바이트를 빅엔디언 정수로 읽어 `% 1,000,000`한 6자리를 `"ddd ddd"`로 쓴다(`PublicKey::confirmation_code`, 고정 테스트 벡터 있음). 바꾸면 `PROTOCOL_VERSION`을 올린다.
- 에이전트는 시작할 때와 대기 중일 때 로그에 코드를 찍는다. 서비스로 돌아 로그를 보기 어려우면 `nodeloom-agent pairing-code`로 확인한다(신원 파일을 만들지 않음).
- UI는 코드·호스트명·ID가 겹치는 요청, 이미 승인된 기기와 이름이 같은 요청에 표시를 달고, 승인 버튼을 두 번 누르게 한다. 두 번째 단계에는 호스트명·코드·주소를 함께 보여 준다. 이름은 NFKC로 접고 공백·대소문자를 무시해 비교한다. 다른 문자 체계의 닮은 글자(예: 키릴 문자 о)는 잡지 못한다.
- 같은 키가 다시 접속해 자기 요청을 바꿔도 목록 순서는 그대로다. 다시 접속해 카드 순서를 뒤섞는 방법으로 클릭을 엉뚱한 카드에 유도할 수 없다.

### 대기 목록 상한

- 같은 IP에서 2개까지 둔다. 더 오면 그 IP의 가장 오래된 요청을 밀어낸다. 같은 키가 다시 접속하면 이전 요청을 바꾼다.
- 전체 32개. 넘으면 새 요청을 거부한다.
- `Origin` 헤더가 있는 `/ws/agent` 업그레이드는 403. 브라우저는 WebSocket에 CORS를 적용하지 않고 항상 Origin을 보내므로, 사용자가 연 웹 페이지가 대기 목록을 채우는 것을 막는다. 에이전트는 Origin을 보내지 않는다.

### 승인·무시·제거

| 동작 | 결과 | 저장 |
|---|---|---|
| 승인 | 대기 연결에 Welcome. 같은 ID로 대기 중인 다른 요청은 거부 | `devices.json`에 추가 |
| 무시 | 대기 연결에 Rejected. 마스터 재시작 전까지 같은 키는 다시 대기 목록에 오르지 않음(최대 256개 기억) | 저장 안 함 |
| 제거 | 연결 중이면 즉시 Rejected로 끊고 작업을 다른 기기로 재배정. 그 키는 영구 거부 | 승인 목록에서 빼고 `revoked`에 추가 |

- 마스터 데이터 폴더: `--data-dir`(env `NODELOOM_DATA_DIR`), 기본은 로컬 데이터 폴더의 `nodeloom/master/`.
  - `devices.json`: `{version, approved:[{id, name, public_key}], revoked:[public_key]}`. 공개키만 있어 유출돼도 접속할 수 없다. 다만 고치면 기기를 들일 수 있으므로 0600으로 쓴다.
  - 깨진 `devices.json`이면 마스터가 시작을 거부한다. 빈 목록으로 시작하면 제거 기록이 사라지기 때문이다.
- 저장은 디스크에 먼저 쓰고 성공하면 메모리를 바꾼다(실패하면 500, 아무것도 안 바뀜). 승인·무시·제거는 저장소 락 → 상태 락 순서로 잡아, 동시에 눌러도 저장 내용이 엇갈리지 않는다.
- 파일 쓰기(`private_file`)는 같은 폴더의 임시 파일에 전부 쓰고 fsync한 뒤, 새 파일은 하드 링크로, 교체는 rename으로 드러낸다. 유닉스에서는 폴더도 fsync한다. 그래서 정전이 나도 "제거했다"고 답한 기록이 사라지지 않고, 에이전트 두 개가 동시에 처음 시작해도 반쯤 쓴 신원 파일을 읽지 않는다.

### 복구

| 상황 | 사용자가 보는 것 | 할 일 |
|---|---|---|
| 마스터 데이터 폴더를 지움·재설치 | 토큰 없이 붙던 기기는 대기 목록에 다시 뜬다(같은 코드). `--token`으로 붙던 기기는 관리 토큰이 새로 만들어져 "wrong token"으로 거부되고 대기 목록에도 안 뜬다(마스터를 `--token`으로 고정해 둔 경우는 제외) | 다시 승인. 토큰 기기는 새 토큰으로 다시 시작하거나 토큰 없이 시작해 승인 |
| 에이전트 신원 파일을 지움 | 새 ID·새 코드로 대기 목록에 뜬다. 이전 항목은 오프라인으로 남는다 | 승인하고 이전 항목은 제거 |
| 기기를 제거함 | 그 기기는 "removed" 이유로 계속 거부된다 | 그 기기에서 `nodeloom-agent reset-identity` 후 새 코드로 승인 |
| 신원 파일이 깨짐 | 에이전트가 시작하지 않는다 | 고치거나 `reset-identity` |
| 관리 토큰 유출 | - | 마스터를 멈추고 `nodeloom-master --rotate-admin-token`으로 한 번 시작한다. 마스터가 이미 그 포트로 실행 중이면 포트를 못 잡아 토큰을 바꾸지 않고 끝난다 |
| `--token`으로 붙은 기기를 제거함 | 그 기기의 키는 거부되지만, 그 기기 디스크(서비스 설정 등)에 관리 토큰이 남아 있다 | 관리 토큰도 바꾼다(UI 제거 확인 화면에도 안내) |

## 메시지 흐름 (WebSocket, JSON, `type` 필드로 구분)

```
(핸드셰이크: 위 "페어링" 참고. Welcome 뒤부터 아래 메시지가 오간다)
agent → master   Metrics(...)                           주기적 자원 보고 (기본 1초)
master → agent   AssignTask(TaskSpec)                   작업 배정
agent → master   TaskProgress { task_id, frames_done, frames_total }
agent → master   TaskDone { task_id } | TaskFailed { task_id, error }
master → agent   CancelTask { task_id }
master → agent   Rejected { reason }                    기기가 제거되면 보내고 연결을 끊는다
```

- `PROTOCOL_VERSION`이 다르면 연결을 거부한다. 호환되지 않는 메시지 변경 시 올린다.
- WebSocket 메시지 최대 1MB, HTTP 요청 본문 최대 64KB.

## 작업과 스케줄링 (`nodeloom-master/src/state.rs`)

- **작업(job)** 은 프레임 범위 하나다. 제출 시점에 그 작업을 실행할 수 있는 기기 수만큼 연속된 구간의 **태스크(task)** 로 나눈다(`nodeloom_core::split::split_frames`). 실행할 기기가 없으면 409를 돌려준다.
- 대기 중인 태스크는 실행 중 태스크가 가장 적은 기기에 배정한다.
- 기기가 끊기면 그 기기의 실행 중 태스크를 대기로 되돌리고(진행률 0) 다른 기기에 다시 배정한다. 같은 ID로 다시 접속해도 이전 세션의 태스크는 다시 배정한다.
- 에이전트는 **자기에게 배정된 태스크만** 진행·완료·실패로 바꿀 수 있다.
- 메모리에는 최근 작업 100개만 둔다. 끝난 작업부터 지운다. 마스터를 재시작하면 작업 기록은 사라진다(영속 저장 없음).

## 대시보드 제공 (`nodeloom-master/src/ui.rs`, D15)

- 릴리즈 빌드(`embed-ui` 기능)는 `apps/desktop/dist`를 마스터 바이너리에 넣고, API가 쓰지 않는 모든 경로에서 대시보드를 제공한다. 그래서 브라우저로 `http://<마스터>:7878`만 열면 된다. 기능 없이 빌드한 마스터(개발용)는 안내 페이지만 보여 준다.
- 페이지 응답에는 CSP를 붙인다. 다른 사이트가 대시보드를 프레임에 넣지 못하게 하고(승인 버튼 클릭재킹 방지), 스크립트는 마스터에서만 받는다. `connect-src`는 다른 마스터에도 접속할 수 있도록 열어 둔다.
- 마스터가 관리 토큰을 처음 만들면 `http://<마스터 IP>:7878/#token=<토큰>` 링크를 한 번 출력한다. URL 조각(`#…`)은 서버로 전송되지 않는다. 페이지는 토큰을 저장한 뒤 주소창에서 지운다.
- 페이지 자체에는 인증이 없다. 보여 주는 정보는 모두 토큰이 필요한 API에서 온다.

## UI용 API (`nodeloom-master/src/server.rs`)

| 경로 | 설명 |
|---|---|
| `GET /api/state` | 전체 스냅샷 `ClusterSnapshot`(연결된 기기, 작업, 승인 대기, 승인된 기기) |
| `POST /api/jobs` | `SubmitJob { payload }` 제출. 400 잘못된 작업, 409 실행 가능한 기기 없음 |
| `POST /api/pending/{public_key}/approve` | 대기 기기 승인. 204, 404 대기 중 아님, 409 ID·키 충돌, 500 저장 실패 |
| `POST /api/pending/{public_key}/ignore` | 대기 기기 무시. 204, 404 |
| `DELETE /api/devices/{node_id}` | 승인된 기기 제거(키 영구 거부). 204, 404, 500 |
| `GET /ws/ui` | 스냅샷 스트림. 연결 직후 한 번, 이후 변경 시마다(최대 초당 약 10회) |
| `GET /ws/agent` | 에이전트 전용(위 핸드셰이크). `Origin` 헤더가 있으면 403 |

- 인증: **관리 토큰**을 `Authorization: Bearer <토큰>`으로 보낸다. `/ws/ui`만 `?token=<토큰>`도 받는다(브라우저 WebSocket은 헤더를 못 넣기 때문). 주소창·로그에 토큰이 남지 않도록 HTTP API는 헤더만 받는다.
- 관리 토큰은 마스터가 처음 시작할 때 만들어 데이터 폴더의 `admin-token`(0600)에 저장하고, 그때 한 번만 출력한다. 이후에는 파일 경로만 출력한다. `--token`/`NODELOOM_TOKEN`으로 덮어쓰고, `--rotate-admin-token`으로 새로 만든다. 루프백(같은 기기) 접속도 예외 없이 토큰이 필요하다. CORS가 모든 출처를 허용하므로, 예외를 두면 사용자가 연 아무 웹 페이지나 API를 부를 수 있기 때문이다.
- CORS는 모든 출처를 허용한다. 쿠키가 아니라 토큰 인증이라 CSRF 위험이 없기 때문이다.

## 러너 (`Runner` 트레이트, `nodeloom-core/src/runner.rs`)

- 작업 종류마다 러너가 하나다. `TaskPayload`의 각 변형이 정확히 하나의 러너에 대응한다.
- `FakeRunner`: 프레임마다 잠깐 쉬기만 한다. 테스트용이며 에이전트에서는 `--enable-fake-runner`로만 켠다.
- `BlenderRunner` (`nodeloom-runner-blender`): Blender를 찾아(맥 앱 경로, 윈도우 기본 설치 경로, PATH) 다음처럼 실행한다.
  `blender --background --disable-autoexec <작업폴더>/<파일> --render-output <작업폴더>/renders/frame_#### --frame-start N --frame-end M --render-anim`
  표준 출력의 `Saved:` 줄 수로 진행률을 계산한다. 결과물은 각 기기의 `renders/`에 남는다(수집 기능 미구현).
- 새 작업 종류를 추가하는 순서: `TaskPayload` 변형 추가(proto, 이슈에서 합의) → `validate_payload` 규칙 → 러너 구현과 테스트 → 에이전트에 등록 → UI 타입·폼.

## 보안 모델

- 기기는 화면 승인(또는 관리 토큰)을 거쳐야 클러스터에 들어온다. 이후에는 기기별 Ed25519 키로 매번 증명한다. UI API는 관리 토큰이 필요하고 비교는 `tokens_match`(상수 시간)로 한다.
- 작업은 닫힌 enum이라 에이전트가 모르는 종류(예: 셸 명령)는 역직렬화 단계에서 거부된다.
- 파일 경로는 상대 경로만 허용하고 `..`, 절대 경로, 드라이브 문자, 역슬래시를 거부한다. 마스터와 에이전트 양쪽에서 검사한다.
- **현재 통신은 암호화되지 않는다.** 관리 토큰이 평문으로 오가므로 신뢰하는 네트워크에서만 쓴다. TLS는 #6에서 다룬다.

### 위협 모델 (페어링 기준)

| 공격자 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|
| 같은 네트워크에서 포트에 접속만 가능(엿보기 불가) | 대기 요청을 만든다(IP당 2, 전체 32). 요청을 많이 만들어 새 기기의 페어링을 늦출 수 있다. mDNS로 마스터가 있다는 것을 안다 | 승인 없이 작업·클러스터 정보 받기, 결과 보고하기. 키 없이 승인된 기기 사칭(서명 검증). 기록한 서명 재사용(매번 새 nonce). 기기 키로 UI API 쓰기(기기 키는 토큰이 아님) |
| 사용자가 연 웹 페이지 | UI API는 토큰이 없어 못 부른다 | `/ws/agent` 접속(Origin 403) |
| 가짜 마스터(mDNS 응답을 먼저 보냄) | 에이전트가 붙으면 그 연결 하나를 진짜 마스터로 중계할 수 있다(TLS 전에는 막을 수 없음). `--master`에 `mac.local` 같은 이름을 주면 운영체제가 그 이름을 mDNS·LLMNR로 풀 수 있어, 거기에 먼저 답한 가짜 마스터가 `--token`의 관리 토큰을 받을 수 있다(에이전트가 경고를 띄운다) | 재사용할 비밀을 얻지 못한다(비밀키는 안 보냄, 서명은 그 nonce에만 유효). 탐색으로 찾은 마스터에는 관리 토큰을 보내지 않는다. `--token`은 `--master`에 IP 주소를 줄 때 안전하다 |
| 트래픽을 엿볼 수 있음 | 관리 토큰을 훔친다 → 관리자 권한. 그래서 "신뢰하는 네트워크" 전제를 유지한다 | 기기 키를 훔치지는 못한다 |
| 승인된 기기의 디스크를 가짐 | 그 기기의 키를 가져가 그 기기로 행세한다 | UI에서 그 기기를 제거하면 그 키는 영구 거부된다 |
| 사칭 기기를 승인하게 유도 | 같은 호스트명으로 대기 요청을 띄운다. 진짜 기기의 코드를 미리 알면(화면을 엿봄) 6자리가 같은 키를 금방 만들 수 있다 | 코드를 모르면 맞출 수 없다(100만 분의 1). 같은 코드·이름·ID가 둘 이상 뜨면 UI가 경고하고 한 번 더 묻는다 |

- TLS(#6) 도입 시 확인 코드에 마스터 인증서 지문을 섞어 가짜 마스터의 중계까지 막는다.

## 빌드 구성

- Rust 워크스페이스는 `crates/*`만 포함한다. Tauri 셸(`apps/desktop/src-tauri`)은 GUI 시스템 라이브러리가 필요해서 워크스페이스에서 빼고 따로 빌드한다.
- UI는 Vite + Svelte 5 + TypeScript 6이다. svelte-check가 TypeScript 7을 단독으로 지원하지 않아 6에 고정했다.
- 지원 플랫폼과 빌드(D14):

| 플랫폼 | 타깃 | CI 테스트 | 배포 바이너리 |
|---|---|---|---|
| 리눅스 x64 | `x86_64-unknown-linux-musl` | `ubuntu-latest` | 정적 링크 |
| 리눅스 arm64 (라즈베리파이 4·5, Jetson) | `aarch64-unknown-linux-musl` | `ubuntu-24.04-arm` | 정적 링크 |
| 윈도우 x64 | `x86_64-pc-windows-msvc` | `windows-latest` | |
| 윈도우 arm64 | `aarch64-pc-windows-msvc` | `windows-11-arm` | |
| macOS arm64 | `aarch64-apple-darwin` | `macos-latest` | |

  - 테스트는 각 아키텍처의 러너에서 그대로 돌린다(교차 컴파일 아님). CI 테스트는 glibc 빌드로, 배포 바이너리는 위 타깃으로 만든다.
  - 리눅스 배포 바이너리를 musl 정적 링크로 만드는 이유: 라즈베리파이 OS(Bookworm, glibc 2.36)와 JetPack(Ubuntu 20.04·22.04, glibc 2.31·2.35)은 빌드 러너(Ubuntu 24.04, glibc 2.39)보다 glibc가 오래돼, glibc에 링크한 바이너리는 실행되지 않는다. 의존성에 C 코드가 없어 musl용 별도 도구 없이 빌드된다.
  - 의존성에 C 코드나 OpenSSL을 넣으면 이 전제가 깨진다. 넣기 전에 musl·윈도우 ARM 빌드를 확인한다.
